## A. RESUMO EXECUTIVO

Após investigação profunda, o commit inicial em linha 142 (`checkpoint.status = "PROCESSING"`) **TEM propósito real**:

1. **É uma reserva/lease:** Marca que este worker está processando
2. **Protege contra concorrência:** Outro worker não processará o mesmo batch
3. **Permite recuperação:** Se worker cair, scheduler pode recuperar após timeout
4. **Mas há lacunas:** A recuperação funciona, mas o ProjectionWorker aparentemente não é executado pelo Scheduler

## B. CHECKPOINT ARCHITECTURE

### Model: `ProjectionCheckpoint`

**Arquivo:** `database/models.py:597-610`

```python
class ProjectionCheckpoint(Base):
    consumer_id = Column(String(64), primary_key=True)  # Unique per worker
    last_processed_event_id = Column(String(64), nullable=True)
    last_processed_at = Column(DateTime(timezone=True), nullable=True)
    status = Column(String(32), default="INITIALIZED")  # INITIALIZED → PROCESSING → IDLE → ERROR
    error_count = Column(Integer, default=0)
    updated_at = Column(DateTime(timezone=True), default=utc_now, onupdate=utc_now)
```

**Estados:**
- `INITIALIZED`: Just created
- `PROCESSING`: Worker is actively processing  ← Commit in line 142
- `IDLE`: Worker finished processing normally
- `ERROR`: Worker encountered error

**O QUE ESTÁ FALTANDO:**
- ❌ Sem timestamp (lease/timeout)
- ❌ Sem worker_id (apenas consumer_id)
- ❌ Sem event_id
- ❌ Sem lock

**Consequência:** Sem timestamp, o sistema não sabe quando um PROCESSING foi abandonado. Precisa de timeout hardcoded (300 segundos).

### Semântica de PROCESSING

**É uma reserva**, não apenas um estado visual:

1. **Reserva:** Worker A toma a checkpoint marcando-o como PROCESSING
2. **Proteção:** Worker B vê PROCESSING e não processa (implementação necessária)
3. **Timeout:** Se worker cai, scheduler espera 300s e recupera

## C. FLUXO ATUAL

### consume_and_project() — Linhas 125-230

```python
# Fase 0: Setup
checkpoint = self._get_or_create_checkpoint()
checkpoint.status = "PROCESSING"
self.db_session.commit()  # ← COMMIT 1 (Reserva)

try:
    # Fase 1: Consumir eventos
    events = self._event_consumer.consume_pending(mission_id, limit)
    
    # Fase 2: Processar eventos (loop)
    for event in events:
        try:
            if self._project_event(event):  # ← Flush, não commit
                self._event_consumer.mark_completed(event.event_id)  # ← ACK
                checkpoint.last_processed_event_id = event.event_id
                checkpoint.error_count = 0
        except Exception as e:
            self._event_consumer.mark_failed(event.event_id, str(e), retry=True)
            checkpoint.error_count += 1
    
    # Fase 3: Finalizar
    checkpoint.status = "IDLE"
    self.db_session.commit()  # ← COMMIT 2 (Checkpoint de sucesso)

except Exception as e:
    checkpoint.status = "ERROR"
    self.db_session.commit()  # ← COMMIT 3 (Checkpoint de erro)
    raise
```

### Separação de Transações

**Transação 1 (Reserva):**
- checkpoint.status = "PROCESSING" commitado
- Propósito: Marcar que este worker tem direito de processar

**Transação 2+ (Projeção):**
- AgentEvent + WebSocketEventLog + ProcessedEvent (flush, não commit)
- Propósito: Processar eventos atomicamente

**Transação 3 (Checkpoint Final):**
- checkpoint.status = "IDLE" ou "ERROR" commitado
- Propósito: Registrar resultado final

## D. CENÁRIOS DE FALHA ANALISADOS

### Cenário A: Checkpoint PROCESSING, Worker cai

```
Timestamp: T0
  checkpoint.status = "PROCESSING" commitado ✓
  Worker executa consume_and_project()
  
Timestamp: T1 (worker cai)
  Partial projections em flush, não commitadas
  checkpoint.status = "PROCESSING" (ainda)
  
Timestamp: T2+300s (scheduler)
  _recover_expired_events() chamado
  recover_expired_processing_events() resets events em PENDING
  Próximo scheduler run: consume_and_project() processa novamente
  
Resultado:
  ✓ Eventos recuperados
  ⚠️ Checkpoint fica em PROCESSING até próximo scheduler run
```

**Estado Final:** OK (eventos reprocessados), mas checkpoint stuck em PENDING

### Cenário B: AgentEvent criado, Web SocketEventLog falha

```
_project_event():
  add(agent_event)
  flush() ✓
  
  log_event():
    add(websocket_event)
    flush() ✓
    
    IntegrityError (UNIQUE violation)
    raise  ← Propaga
  
  except Exception:
    self.db_session.rollback()  ✓
    raise  ← Propaga

consume_and_project():
  except Exception:
    self._event_consumer.mark_failed(event.event_id, ..., retry=True)
    checkpoint.error_count += 1

Resultado:
  ✓ Ambas AgentEvent + WebSocketEventLog rolled back
  ✓ Evento marcado como FAILED com retry
  ⚠️ Checkpoint.status ainda = "PROCESSING"
```

**Estado Final:** Atomicidade respeitada (ambas rolledback), mas checkpoint stuck

### Cenário C: PostgreSQL commit sucede, SQLite ACK falha

```
_project_event() retorna True

self._event_consumer.mark_completed(event.event_id)
  ← mark_completed() em SQLite

Se mark_completed() falha:
  except Exception (linha 207)
  self._event_consumer.mark_failed(...)
  checkpoint.error_count += 1

Resultado:
  ✓ PostgreSQL commitado
  ✗ SQLite ACK falhado
  Evento é reprocessado (porque não foi ACKed)
```

**Estado Final:** Duplicação possível se PostgreSQL não é idempotente

### Cenário D: Dois Workers tentam processar simultaneamente

```
Worker A:
  checkpoint.status = "PROCESSING" ✓ Commitado

Worker B:
  checkpoint.status = "PROCESSING" (atualizar mesmo record)
  
Sem lock:
  Worker A: checkpoint.status = "IDLE" ✓
  Worker B: checkpoint.status = "IDLE" ✓
  
Resultado:
  ✓ Ambas trabalham (somente uma deveria)
  Risco: Duplicação de processamento
```

**Estado Final:** Race condition — sem proteção contra concorrência simultânea

## E. CONTRATOS TRANSACIONAIS ATUAIS

### Contrato 1 — Reserva (Lease)

```
BEGIN
  checkpoint.status = PROCESSING
COMMIT
```

**Propósito:** Marcar direito de processar  
**Duração:** Enquanto consume_and_project() roda  
**Timeout:** 300 segundos (scheduler)  
**Proteção:** Apenas timeout, sem lock ativo  
**Risco:** Outro worker pode não respeitar a reserva

### Contrato 2 — Projeção (Flush)

```
BEGIN (implícito, compartilhado com reserva)
  add(AgentEvent)
  flush()
  
  add(WebSocketEventLog)
  flush()
  
  add(ProcessedEvent) [se aplicável]
  flush()
  
COMMIT (somente ao final)
```

**Propósito:** Atomicidade de projeções  
**Flushed:** Todos (validação de constraints)  
**Committed:** Nenhum (reservado para Contrato 3)  
**Risco:** Checkpoint já foi commitado (Contrato 1)

### Contrato 3 — Checkpoint Final

```
BEGIN
  checkpoint.status = IDLE ou ERROR
COMMIT
```

**Propósito:** Registrar finalização  
**Separado:** De Contratos 1 e 2  
**Risco:** Se fails, checkpoint.status fica em PROCESSING

### Contrato 4 — ACK (EventBus)

```
após _project_event() retorna True:
  self._event_consumer.mark_completed(event.event_id)
```

**Ordem:** DEPOIS de projeção, ANTES de checkpoint final  
**Risco:** Se mark_completed() falha, evento é reprocessado (correto)  
**Risco:** Se PostgreSQL commitado mas SQLite falha → duplicação possível

## F. RECOVERY ARCHITECTURE

### Scheduler — `app/core/scheduler.py:97-150`

**Intervalo:** 10 segundos (padrão)  
**Fases:**

1. **Phase 1:** Publicar Outbox events
2. **Phase 2:** Recuperar PROCESSING expirado (timeout 300s)
3. **Phase 3:** Executar ProjectionWorker

### Recovery — `_recover_expired_events()` linha 208

```python
for tenant_id, project_id in query.all():
    recovered = recover_expired_processing_events(
        tenant_id=tenant_id,
        project_id=project_id,
        max_processing_age_seconds=300  # 5 minutos
    )
```

**Lógica:**
- Para cada tenant/project
- Se checkpoint.updated_at > 300 segundos atrás
- Reset events em PENDING para reprocessamento

**Problema:** ProjectionWorker é chamado no scheduler (linha 240) mas no Scheduler wrapper é vazio (`pass`).

## G. CONCORRÊNCIA ANALYSIS

### Proteções Atuais

| Mecanismo | Status | Efetividade |
|-----------|--------|-------------|
| Lock de banco | ❌ Não | Sem row lock |
| Lease com timeout | ⚠️ Sim | Apenas timeout, sem ativo |
| consumer_id (PK) | ✅ Sim | Um worker por consumer_id |
| UNIQUE constraint | ✅ Sim | event_id não duplicado |
| Idempotência | ✅ Sim | log_event() verifica existing |

### Vulnerabilidades

1. **Dois ProjectionWorkers simultâneos:**
   - Ambos veem checkpoint em IDLE
   - Ambos marcam como PROCESSING
   - Ambos processam mesmos eventos
   - Risco: **DUPLICAÇÃO**

2. **Worker A processando, Worker B iniciando:**
   - Worker B não vê que checkpoint está em PROCESSING
   - Sem lock ativo, Worker B entra
   - **RACE CONDITION**

3. **Scheduler recovery + Worker simultâneos:**
   - Scheduler recupera PROCESSING antigo
   - Worker novo está processando mesmo evento
   - **DUPLICAÇÃO POSSÍVEL**

---

## H. LACUNAS IDENTIFICADAS

1. **Sem lock ativo:** checkpoint.status é só informativo
2. **Sem timestamp no checkpoint:** Precisa timeout hardcoded
3. **Sem worker_id:** Não rastreia qual worker tinha reserva
4. **ProjectionWorker não executado pelo Scheduler:** Implementação incompleta
5. **Sem proteção contra concorrência:** Dois workers podem processar simultaneamente
6. **Checkpoint stuck em PROCESSING:** Se worker cai, estado fica indefinido até timeout

---

## I. OPÇÕES DE CORREÇÃO

### Opção 1 — Manter Separação, Adicionar Proteção

**Manter:**
- Checkpoint.status = PROCESSING como reserva
- Separação de transações (1. Reserva, 2. Projeção, 3. Finalizar)

**Adicionar:**
- Row-level lock no checkpoint para evitar race condition
- Timestamp no checkpoint (lease/timeout explícito)
- Worker ID para rastreabilidade
- Validação em consume_and_project(): se checkpoint.status ≠ INITIALIZED, skip

**Complexidade:** Alta (adicionar lock e validações)

### Opção 2 — Único Commit para Tudo

**Mudar:**
- Remover Contrato 1 (reserva separada)
- Único commit para checkpoint + projections

**Risco:**
- Perde proteção contra processamento simultâneo
- Precisa implementar lock explícito se precisar de serialização
- Ou aceitar duplicação e tornar idempotência mais robusta

**Complexidade:** Média (refatorar consume_and_project)

### Opção 3 — Manter Separação, Melhorar Recovery

**Manter:**
- Separação de transações (melhor para concorrência)

**Melhorar:**
- Implementar lock pessimista em checkpoint
- Adicionar timestamp com lease explícito
- Garantir ProjectionWorker é executado pelo Scheduler
- Adicionar validações de concorrência

**Complexidade:** Alta (implementação mais robusta)

## J. RECOMENDAÇÃO

**Opção 3 é a mais segura**, pois:

1. ✅ Preserva separação (melhor para concorrência)
2. ✅ Adiciona proteções necessárias (lock, timeout, validação)
3. ✅ Melhora recovery (ProjectionWorker realmente executado)
4. ✅ Mantém semântica de reserva (importante para distributed workers)

**Critérios para Implementação:**

1. **Lock pessimista:** `SELECT * FROM checkpoint WHERE consumer_id = ? FOR UPDATE`
2. **Timestamp com lease:** Adicionar `lease_until` ao model
3. **Worker validation:** Verificar `lease_until > now()` antes de processar
4. **ProjectionWorker no Scheduler:** Implementar real execution (não `pass`)
5. **Multi-worker safety:** Testar com 2+ workers simultâneos

---

## K. CONCLUSÃO

O commit inicial em linha 142 **NÃO é um erro**, é uma reserva intencional. Mas:

- **Proteção:** Incompleta (sem lock ativo)
- **Recovery:** Funciona mas está marcada como teste (`pass`)
- **Concorrência:** Vulnerável a race conditions
- **State consistency:** Checkpoint pode ficar stuck

**Remover arbitrariamente o commit quebraria o mecanismo de reserva.**

**Solução:** Adicionar proteções sem remover separação de transações.
