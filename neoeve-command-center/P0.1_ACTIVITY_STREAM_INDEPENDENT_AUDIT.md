## C. ATOMICIDADE — VIOLAÇÃO CRÍTICA

### ❌ PROBLEMA 1: Dois Commits Separados

**Local:** `websocket_event_log_service.py:81` vs `projection_worker.py:219`

**Fluxo Transacional Real:**

```
consume_and_project() INICIA transação
    ↓
_project_event(event)
    ├─ add(agent_event)
    ├─ flush()  [Validação de constraints, mas não commit]
    ├─ log_event()
    │   ├─ add(websocket_event)
    │   └─ commit()  ← PRIMEIRO COMMIT aqui (linha 81)
    │       └─ WebSocketEventLog agora permanente
    └─ return True
    ↓
consume_and_project() continua...
    └─ db.commit()  ← SEGUNDO COMMIT aqui (linha 219)
        └─ AgentEvent agora permanente
```

**Violação:** Atomicidade QUEBRADA

**Cenário de Falha:**

```
1. WebSocketEventLog.log_event() → db.commit() ✓ (WebSocketEventLog persistido)
2. Alguma outra operação em consume_and_project() lança exceção
3. db_session.rollback() em linha 229 → Rollback tudo
4. Resultado: AgentEvent não foi commitado (ainda está em flush), 
   mas WebSocketEventLog JÁ FOI commitado (primeiro commit)
```

**Consequência:**
- Activity Stream tem evento órfão (sem correspondente em AgentEvent)
- Garantia de atomicidade: **QUEBRADA**
- Garantia de não-fatal failure: **VIOLADA** (não é verdadeiramente não-fatal se WebSocketEventLog fica órfão)

### Recomendação

Remover `db.commit()` de dentro de `log_event()`. Deixar que o caller controle a transação.

## D. NON-FATAL FAILURE — PROBLEMA DE LÓGICA

### ❌ PROBLEMA 2: Non-Fatal Failure Sem Idempotência em Retry

**Local:** `websocket_event_log_service.py:90-93`

```python
except Exception as e:
    logger.error(f"Failed to log WebSocket event {event_id}: {e}")
    db.rollback()
    return None
```

**Situação de Retry:**

```
Primeira tentativa:
1. log_event() falha por erro transiente (DB timeout)
2. Retorna None
3. Warning é logado
4. _project_event() retorna True (sucesso)

Retry (segunda tentativa do mesmo evento):
1. AgentEvent INSERT falha com UNIQUE (já existe da primeira tentativa bem-sucedida)
2. É capturado em linha 272, retorna True (idempotente, OK)
3. log_event() tenta novamente
4. Falha com UNIQUE em event_id (primeira tentativa era no mesmo dia)
5. Retorna None novamente
6. Warning é logado novamente

Resultado: Mesmo evento processado 2x, mas WebSocketEventLog com apenas 1 entrada
Essa é a idempotência correta, mas...
```

**Problema Real:**

Se a falha em `log_event()` for por motivo diferente de UNIQUE (ex: DB connection lost), retry pode levar a duplicação:

```
Primeira tentativa:
1. ws_log_service.log_event(...) ← Connection lost mid-INSERT
2. Partial INSERT → db.rollback()
3. Event não foi inserido

Retry:
1. ws_log_service.log_event(...) ← Sucesso
2. Event foi inserido

Resultado: OK (idempotente graças à UNIQUE)
```

**Mas há risco silencioso:**

Se UNIQUE constraint não existisse, haveria duplicação sem aviso. O try-catch em `_project_event()` não valida idempotência.

## K. ACHADOS DETALHADOS

### 🔴 CRÍTICO #1: Duplos Commits Quebram Atomicidade

**Arquivo:** `websocket_event_log_service.py:81`  
**Severidade:** CRÍTICA  
**Impacto:** Quebra completamente a garantia de atomicidade

**Descrição:**
O método `log_event()` faz `db.commit()` imediatamente, enquanto o caller (`_project_event()`) também faz `db.commit()` mais tarde. Isso cria dois commits separados, violando atomicidade.

**Teste:**
```python
# Se acontecer exceção após log_event().commit() mas antes do segundo commit()
# Resultado: WebSocketEventLog persistido, AgentEvent em estado inconsistente
```

**Correção Necessária:**
Remover `db.commit()` de dentro de `log_event()`, deixar que o caller controle transação.

---

### 🔴 CRÍTICO #2: Non-Fatal Failure Sem Atomicidade Real

**Arquivo:** `projection_worker.py:325-330`  
**Severidade:** CRÍTICA  
**Impacto:** Falsa promessa de "non-fatal failure"

**Descrição:**
O try-catch captura falhas em `log_event()` e apenas loga warning, retornando True no final. Mas se a falha foi silenciosa (ex: partial INSERT), não há rollback do commit anterior de `log_event()`.

**Resultado:** Inconsistência de dados silenciosa

---

### 🔴 CRÍTICO #3: Sem Proteção de Validação de Idempotência em Código

**Arquivo:** `websocket_event_log_service.py:70-88`  
**Severidade:** ALTA  
**Impacto:** Idempotência depende apenas de constraint, sem validação em código

**Descrição:**
Se UNIQUE constraint falhar ou não existir, não há tratamento de UNIQUE violation. Silenciosamente retorna None e faz rollback.

**Correção Necessária:**
Tratar UNIQUE violation explicitamente como caso idempotente (não erro).
