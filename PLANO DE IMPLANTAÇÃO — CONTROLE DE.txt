PLANO DE IMPLANTAÇÃO — CONTROLE DE PLANOS NEOEVE

Versão: 1.0
Status: Planejamento
Objetivo: Fazer a NeoEve distinguir, liberar e limitar corretamente os planos Solo, Solo Pro, Studio, Salão e Pro, de forma determinística, multi-tenant, auditável e sem regressão na agenda.

1. Objetivo da implantação

Criar um sistema centralizado de autorização comercial que determine, para cada tenant:

qual plano está contratado;
qual é o estado atual da assinatura;
quais funcionalidades estão liberadas;
quais limites quantitativos se aplicam;
quais operações devem ser bloqueadas;
qual plano mínimo libera determinado recurso;
como upgrade, downgrade, trial e cancelamento alteram o acesso;
como todas as decisões ficam registradas no histórico.

O resultado esperado é impedir situações como:

cliente Solo utilizando relatórios do Salão;
cliente Solo cadastrando vários profissionais;
plano encerrado continuando com acesso total;
trial liberando funcionalidades indefinidas;
downgrade apagando profissionais ou agendas;
dois cadastros simultâneos ultrapassando o limite;
tenant utilizando plano ou assinatura de outro tenant;
GPT decidindo acesso, limite ou plano.
2. Princípios obrigatórios
2.1 GPT não controla autorização

O GPT pode interpretar frases como:

“Quero cadastrar outra manicure.”
“Quero ver meu relatório.”
“Quero mudar para o Studio.”
“Posso adicionar mais uma profissional?”

O GPT retorna somente uma estrutura de intenção.

Exemplo:

{
  "intencao": "cadastrar_profissional",
  "profissional": {
    "nome": "Amanda"
  }
}

A decisão de permitir ou bloquear será sempre executada pelo motor determinístico.

2.2 Fonte única de verdade

O plano atual do tenant deve estar em uma assinatura central.

Não utilizar como fonte definitiva:

texto da sessão;
campo livre produzido por GPT;
parâmetros recebidos diretamente do canal;
listas genéricas como planosAtivos;
flags espalhadas em diferentes documentos;
estado armazenado em memória local.
2.3 Multi-tenant obrigatório

Toda consulta de plano, assinatura, limite ou recurso deve receber explicitamente:

tenant_id

Toda decisão de acesso deve utilizar dados localizados exclusivamente dentro do tenant correspondente.

Nunca buscar assinatura somente por:

actor_id

O ator identifica quem está falando. O tenant identifica de qual negócio são os dados e a assinatura.

2.4 Falha fechada

Quando houver:

plano desconhecido;
assinatura inexistente;
catálogo inválido;
erro de leitura;
configuração inconsistente;
ausência de tenant_id;

o sistema não deve liberar recursos protegidos.

A regra será:

não foi possível comprovar autorização
→ operação protegida bloqueada

Isso não significa interromper indiscriminadamente a agenda. A política de contingência das operações essenciais será definida explicitamente.

2.5 Preservação de dados

Plano e assinatura controlam acesso, não propriedade dos dados.

Upgrade, downgrade, inadimplência ou cancelamento nunca devem:

apagar profissionais;
apagar clientes;
apagar eventos;
apagar sessões;
apagar histórico;
excluir configurações automaticamente.

FASE 3 — Motor central de entitlements
Objetivo

Criar um único ponto de decisão para acesso e limites.

Interface prevista
get_current_subscription(tenant_id)
get_plan_entitlements(tenant_id)
has_feature(tenant_id, feature)
get_limit(tenant_id, resource)

authorize_resource_creation(
    tenant_id,
    actor_id,
    resource,
    current_count
)
authorize_operation(tenant_id, actor_id, operation)
Resultado padronizado

Toda autorização deve retornar estrutura, não apenas True ou False.

{
  "allowed": false,
  "reason": "PLAN_LIMIT_REACHED",
  "plan_id": "STUDIO",
  "required_plan": "SALAO",
  "resource": "professionals",
  "current": 3,
  "limit": 3
}
Códigos de erro mínimos
TENANT_REQUIRED
SUBSCRIPTION_NOT_FOUND
SUBSCRIPTION_NOT_ACTIVE
UNKNOWN_PLAN
INVALID_CATALOG
FEATURE_NOT_AVAILABLE
PLAN_LIMIT_REACHED
TENANT_OVER_LIMIT
AUTHORIZATION_INTERNAL_ERROR
Regras
nenhuma função recebe plano informado pelo GPT;
nenhuma função confia em plan_id vindo do request;
assinatura é carregada pelo tenant_id;
toda decisão pode ser auditada;
cache, se existir, deve ser invalidado em mudança de assinatura;
cache nunca pode misturar tenants.
Entregáveis
plan_entitlement_service;

Critério de aceite

FASE 4 — Limites quantitativos transacionais
Objetivo

Impedir que concorrência ou chamadas paralelas ultrapassem os limites do plano.

Recursos iniciais
profissionais ativos;
agendas ativas;
números dedicados;
outros recursos futuros explicitamente limitados.
Fluxo obrigatório para criação de profissional
receber operação
→ validar tenant
→ carregar assinatura
→ carregar limite
→ contar profissionais ativos dentro de transação/lock
→ comparar
→ criar profissional
→ atualizar contador, se houver
→ registrar auditoria
Concorrência

Não aceitar:

quantidade = contar_profissionais()
if quantidade < limite:
    criar_profissional()

Esse padrão permite race condition.

Usar uma destas estratégias, conforme a arquitetura atual:

transação Firestore;
documento contador com atualização transacional;
lock determinístico por tenant e recurso;
mecanismo equivalente já validado no projeto.
Downgrade acima do limite

Quando o tenant possui mais recursos que o novo plano:

não apagar
não desativar automaticamente
marcar OVER_LIMIT
bloquear expansão
orientar regularização
Entregáveis
serviço de limites;
proteção transacional;
estado OVER_LIMIT;
testes de concorrência.
Critério de aceite

Em duas tentativas simultâneas para ocupar a última vaga, apenas uma operação conclui.

FASE 5 — Inserção dos guards nos recursos

5.2 Criação de agendas

5.3 Relatórios

Feature:

occupancy_reports

Disponível somente em:

O guard deve existir no serviço que gera os dados, não apenas na interface.

5.4 Retenção automática

Features:

client_reactivation

Disponíveis a partir do Solo Pro.

Todo job agendado deve validar:

tenant
→ assinatura
→ estado
→ feature
→ elegibilidade operacional
5.5 Encaixe automático

Feature:

automatic_waitlist

Disponível em todos os planos.

O objetivo do guard aqui é garantir que o recurso não fique acidentalmente restrito a planos superiores.

5.6 Número dedicado

Disponível a partir do Solo Pro.

A autorização não significa provisionamento concluído. O fluxo será:

→ solicitação idempotente
→ provisionamento
→ associação ao tenant
→ ativação
→ histórico
5.7 Onboarding acompanhado

Disponível a partir do Studio.

Inicialmente pode representar:

5.8 Suporte

Features:

Essas flags devem classificar atendimento e fila. Não devem bloquear o usuário de pedir suporte.

Entregáveis

testes de integração por recurso;
documentação dos bloqueios.
Critério de aceite

Não existe caminho alternativo conhecido que execute um recurso protegido sem passar pelo motor de autorização.

FASE 6 — Trial, upgrade, downgrade e cancelamento
Objetivo

Aplicar mudança de acesso com histórico, idempotência e preservação de dados.

6.1 Trial

Todo trial deve possuir:

{
  "status": "TRIAL",
  "plan_id": "SOLO_PRO",
  "trial_started_at": "...",
  "trial_ends_at": "...",
  "catalog_version": 1
}

O plano do trial deve ser definido pelo fluxo comercial, não pelo GPT.

6.2 Upgrade

Fluxo:

solicitação
→ validação comercial
→ confirmação de pagamento
→ transação de assinatura
→ histórico
→ invalidação de cache
→ liberação das novas features
→ provisionamentos necessários

A operação deve ser idempotente.

Repetir o mesmo evento de pagamento não pode executar dois upgrades.

6.3 Downgrade

Fluxo:

solicitação
→ verificar recursos atuais
→ informar impactos
→ agendar mudança
→ aplicar no período correto
→ marcar OVER_LIMIT, quando necessário
→ preservar todos os dados
→ bloquear expansão
6.4 Cancelamento

Distinguir:

cancelamento agendado para o fim do período;
cancelamento imediato;
encerramento após período;
suspensão por falha operacional;
inadimplência.

O cancelamento da assinatura não é o mesmo que cancelar agendamentos de clientes.

Entregáveis
state machine integrada;
eventos idempotentes;
política de mudança de plano;
testes de transição.
Critério de aceite

Toda mudança de plano produz exatamente um novo estado válido, mantém histórico e invalida autorizações antigas.

FASE 7 — Migração dos tenants existentes
Objetivo

Converter os dados atuais para a nova estrutura sem atribuir planos incorretos.

Etapas
Executar inventário dos tenants.
Classificar cada tenant:
plano conhecido;
plano inferível com segurança;
plano ausente;
múltiplos planos;
pagamento inconsistente;
tenant de teste;
tenant desativado.
Gerar relatório de pré-migração.
Não migrar automaticamente casos ambíguos.
Criar modo dry-run.
Comparar:
estado anterior;
plano calculado;
assinatura proposta;
divergências;
riscos.
Executar migração idempotente.
Registrar versão da migração.
Validar tenant por tenant.
Manter rollback lógico.
Política recomendada

Nunca assumir PRO como fallback.

Para tenant sem plano confiável:

status = PENDENTE ou MIGRATION_REVIEW
acesso protegido = bloqueado
dados = preservados
alerta = criado

A política definitiva deve considerar os clientes reais existentes para não interromper indevidamente o serviço.

Entregáveis
script de dry-run;
relatório de divergências;
script idempotente;
resultado JSON;
procedimento de rollback.
Critério de aceite

A quantidade de tenants antes e depois é igual, nenhum dado operacional é apagado e todos os tenants migrados possuem plano conhecido.

Critério de aceite

A restrição entra em produção por camadas, sem desligamento abrupto do núcleo de agenda.

7. Ordem técnica recomendada

A ordem obrigatória será:

1. Auditoria
2. Contrato dos planos
3. Modelo de assinatura
4. Motor de entitlements
5. Serviço transacional de limites
6. Guards dos recursos
7. Trial e mudanças de plano
8. Migração
9. Testes completos
10. Shadow mode
11. Ativação gradual
12. Remoção do legado

Não iniciar pelos bloqueios.

Bloquear recursos antes de criar catálogo, assinatura consolidada e compatibilidade produziria regressões e bloqueios incorretos.

9. Definition of Done geral

A implantação somente será considerada concluída quando:

os cinco planos estiverem definidos em catálogo versionado;
todo tenant possuir assinatura única e válida;
features e limites forem resolvidos deterministicamente;
plano desconhecido falhar fechado;
nenhuma decisão crítica depender de GPT;
criação de profissional respeitar limite transacionalmente;
criação de agenda respeitar limite transacionalmente;
relatórios estiverem restritos a Salão e Pro;
retenção e preferência estiverem restritas a Solo Pro ou superior;
número dedicado estiver restrito a Solo Pro ou superior;
onboarding acompanhado estiver restrito a Studio ou superior;
upgrade e downgrade forem idempotentes;
downgrade não apagar dados;
trial estiver vinculado a um plano;
todas as decisões tiverem auditoria;
isolamento multi-tenant estiver comprovado;
matriz completa de testes estiver verde;
regressão operacional estiver verde;
ativação gradual tiver sido concluída;
legado tiver sido removido ou formalmente isolado.
10. Riscos principais
Risco 1 — Bloquear clientes existentes

Mitigação: shadow mode, migração prévia e preservação de recursos existentes.

Risco 2 — Ultrapassar limites por concorrência

Mitigação: transação ou lock por tenant e recurso.

Risco 3 — Duplicar fontes de verdade

Mitigação: assinatura atual como fonte canônica e camada legada temporária.

Risco 4 — Misturar tenants

Mitigação: tenant_id obrigatório em repository, service, cache, lock e auditoria.

Risco 5 — GPT alterar acesso

Mitigação: catálogo e assinatura nunca recebidos da interpretação GPT.

Risco 6 — Plano comercial e código divergirem

Mitigação: catálogo versionado, matriz aprovada e teste de contrato.

Risco 7 — Downgrade destruir operação

Mitigação: estado OVER_LIMIT, bloqueio de expansão e preservação dos dados.

Risco 8 — Jobs automáticos ignorarem o plano

Mitigação: entitlement obrigatório em cada execução por tenant.

Risco 9 — Webhook duplicado alterar assinatura duas vezes

Mitigação: idempotency key e histórico transacional.

11. Fora do escopo desta implantação

Não faz parte desta entrega inicial:

cálculo financeiro de rentabilidade do plano;
cobrança direta ao cliente final;
criação automática de preço por uso;
plano customizado por tenant;
venda de módulos avulsos;
desconto negociado;
cupom;
comissão;
cobrança por profissional excedente;
mudança automática de plano por uso;
GPT recomendando e executando upgrade;
painel financeiro avançado.

Esses itens podem ser incorporados depois, utilizando o mesmo contrato de assinatura.

12. Resultado esperado

Ao final, o sistema seguirá esta cadeia:

serviço solicitado
→ tenant identificado
→ assinatura validada
→ plano resolvido
→ feature verificada
→ limite verificado
→ conflito operacional analisado, quando aplicável
→ operação criada de forma segura
→ histórico registrado
→ resposta retornada

Exemplo:

Dona pede para cadastrar quarta profissional
→ tenant está no Studio
→ Studio permite até três
→ existem três profissionais ativos
→ motor bloqueia
→ nenhum documento é criado
→ auditoria registra PLAN_LIMIT_REACHED
→ sistema informa que o limite do Studio foi atingido
→ pode apresentar upgrade para Salão

O GPT participa somente da interpretação da mensagem e da formulação da resposta. A autorização, o limite, a escrita e o histórico permanecem determinísticos.
